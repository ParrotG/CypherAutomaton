# IN-CYPHER temporary bridge 工程说明

本文档面向后续接手本项目的 Agent / 开发者，说明当前实现、设计取舍、数据模型、
接口、测试方式和待办事项。

---

## 1. 项目背景

IN-CYPHER Hackathon 是让参赛者构建 autonomous agent 去解 CTF 的比赛。题目
类型包括 web / pwn / network / crypto / rev / forensics / misc 等。平台规则中：

- 静态题目：共享服务或可下载文件。
- isolated 题目：点击 Deploy 后为每个 team 启动独立容器，端口随机，flag 唯一。
- raw TCP 题目：使用 `nc HOST PORT` 连接，连接前有 team-key-bound
  proof-of-work gate。
- web 题目：使用不可猜测子域名的 HTTPS URL，没有 PoW gate。
- 官方 ADK 和 solver 尚未发布，因此需要自己实现临时中间层。

本项目的目标就是实现这个临时中间层：

1. 从安全位置读取 team key；
2. 解析 PoW banner，计算并发送 X；
3. 建立并维持 upstream 连接；
4. 为 Agent 提供本地 TCP 连接；
5. 为人类提供可检查的 status / context / observe / send 接口；
6. 支持题目描述注入和 challenge/run 管理。

当前只负责 raw TCP + PoW 类型；web 题目由 Agent 直接访问 URL。

---

## 2. 当前实现总览

连接级设计仍是“一个 run 一个 upstream + 一个本地 relay endpoint”。
一个 `serve` 进程现在可以通过 `SessionManager` 为同一题目管理多个独立 run：
主 run 和子 run 分别完成 PoW，各自维护端口、缓冲、重连、control socket 和日志。
这只涉及 bridge 会话管理，不包含调度器或 worker agent 的实现。

```text
challenge service
      ^
      | raw TCP / PoW
      |
+-----+-----------------------+
| BridgeSession               |
|  - PoW client               |
|  - upstream reconnect       |
|  - pending buffer           |
|  - local TCP listener       |
|  - Unix control socket      |
|  - EventLogger              |
+-----+-----------------------+
      |
      | tcp://127.0.0.1:<port>
      v
autonomous agent

human <---- status / context / observe / send / stop ----> control socket
```

### 模块职责

| 文件 | 职责 |
| --- | --- |
| `src/incypher_bridge/client.py` | 连接 upstream，解析 PoW banner，尝试多种 PoW 编码，返回 `PrefixedSocket` |
| `src/incypher_bridge/pow.py` | PoW 参数、变体定义、求解与校验 |
| `src/incypher_bridge/config.py` | team key 安全加载、`.env.local` 解析、权限检查 |
| `src/incypher_bridge/paths.py` | `challenge_id` / `run_id` 目录布局、短路径 control socket |
| `src/incypher_bridge/session.py` | `BridgeSession` 生命周期、upstream pump、本地 relay、重连、计时 |
| `src/incypher_bridge/manager.py` | 同题目独立会话创建、幂等 run 标识、会话和握手额度、父子生命周期 |
| `src/incypher_bridge/transcript.py` | `events.jsonl`、`transcript.log`、raw stream 记录、状态格式化 |
| `src/incypher_bridge/control.py` | Unix JSON-lines control server/client |
| `src/incypher_bridge/cli.py` | 人类可读 CLI |
| `src/bridge.py` | `python bridge.py ...` 包装 |
| `src/solver.py` | 官方 `solver.connect` 兼容入口 |

## 3. 数据模型

### challenge

一个问题，例如：

```text
overflow-ward
```

稳定标识，建议每次比赛都用同一个 `challenge_id`，同一题目的多次部署和重连都
落在同一个 challenge 下。

存储路径：

```text
.cypher_bridge/challenges/<challenge_id>/
├── challenge.json
└── challenge.md
```

`challenge.json` 字段：

- `challenge_id`
- `name`
- `category`
- `description`
- `description_file`
- `challenge_md`
- `created_at`
- `updated_at`

### run

`run_id` 表示一次连接实例和解题过程。默认自动生成，例如：

```text
run-20260916T145544Z-2da959
```

存储路径：

```text
.cypher_bridge/challenges/<challenge_id>/runs/<run_id>/
├── run.json
├── events.jsonl
├── transcript.log
├── challenge_to_agent.bin
└── agent_to_challenge.bin
```

`run.json` 主要字段：

- `challenge_id`、`run_id`
- `challenge_name`、`category`
- `description_present`、`description_text`、`description_file`、`challenge_md`
- `host`、`port`、`target`
- `agent_endpoint`
- `state`
- `pow_summary`
- `started_at`、`updated_at`
- `challenge_to_agent_bytes`、`agent_to_challenge_bytes`
- `events`
- `stop_reason`、`last_error`
- `control_socket`

### active.json

`active.json` 记录最近启动/更新的 run，便于人类命令省略 `--challenge-id` /
`--run-id`：

```json
{
  "latest": {
    "challenge_id": "overflow-ward",
    "run_id": "run-...",
    "run_dir": "...",
    "control_socket": "...",
    "state": "running",
    "target": "...",
    "agent_endpoint": "tcp://127.0.0.1:...",
    "updated_at": "..."
  }
}
```

### control socket

control socket 放在 state 目录顶层，例如：

```text
.cypher_bridge/c-<pid>-<rand>.sock
```

原因是 Linux `AF_UNIX` 路径长度约 107 字节，不能放在很深的
`challenges/<id>/runs/<run_id>/` 下面。`run.json` 会记录实际路径。

## 4. CLI 用法

### 启动

```bash
uv run python -m incypher_bridge serve \
  --target 47.236.162.54:30092 \
  --challenge-id overflow-ward \
  --category pwn \
  --description-file /path/to/overflow-ward.md \
  --duration 1h
```

`--run-id` 可选，默认自动生成。`--description-text` 可直接内联描述。

### 人类管理

```bash
uv run python -m incypher_bridge list
uv run python -m incypher_bridge status  --challenge-id overflow-ward --run-id <run>
uv run python -m incypher_bridge context --challenge-id overflow-ward --run-id <run>
uv run python -m incypher_bridge observe --follow --challenge-id overflow-ward --run-id <run>
uv run python -m incypher_bridge send --text 'help\n' --challenge-id overflow-ward --run-id <run>
uv run python -m incypher_bridge reconnect --challenge-id overflow-ward --run-id <run>
uv run python -m incypher_bridge stop --challenge-id overflow-ward --run-id <run>
```

不传 selector 时默认使用 `active.json` 中最新 run。

### 离线 PoW 计算

```bash
uv run python -m incypher_bridge pow-solve \
  --nonce 002f4d0975a5cb4e00c0393495120291 \
  --bits 20
```

## 5. Agent 接入

Agent 连接本地 bridge：

```python
from solver import connect_bridge

s = connect_bridge(46385)
banner = s.recv(4096)
```

或者：

```python
import socket
s = socket.create_connection(("127.0.0.1", 46385))
```

Agent 不需要 team key，也不执行 PoW。

### 题目描述如何交给 Agent

启动 bridge 时传入：

```bash
--description-file ./overflow-ward.md
```

描述会被复制到：

```text
.cypher_bridge/challenges/<challenge_id>/challenge.md
```

run 目录中的 `run.json` 同时包含：

- `description_text`
- `description_file`
- `challenge_md`

因此 Agent 系统可以选择：

1. 直接读取 `challenge.md`；
2. 读取 `run.json` 的 `description_text`；
3. 执行 `incypher_bridge context --json` 获取结构化上下文。

当前 bridge 不会把描述混入 TCP 协议流，避免污染题目交互。

## 6. PoW 协议

平台 PoW banner 示例：

```text
IN-CYPHER pwn instance proof-of-work required (team-key bound)
nonce=3b813612dc09ad98085b2a8f55305547 bits=20
send X such that sha256(hmac_sha256(team_key, nonce) || X) has 20 leading zero bits:
```

默认优先变体：

```python
mac = hmac.new(team_key.encode(), nonce.encode(), hashlib.sha256).digest()
sha256(mac + str(i).encode()).digest()
```

`client.connect` 会依次尝试：

1. raw HMAC digest + ASCII decimal X；
2. raw HMAC digest + raw nonce + ASCII decimal X；
3. raw HMAC digest + ASCII hex X；
4. raw HMAC digest + raw nonce + ASCII hex X；
5. ASCII hex HMAC digest 变体；
6. raw 64-bit X fallback。

如果官方 solver 发布后确认了真实算法，应优先把真实变体放到 `DEFAULT_VARIANTS`
第一位，或移除不必要猜测。

注意：目前观察到某些实例约 30 秒 idle 后 upstream 会断开；`BridgeSession`
默认自动重连并重新过 PoW。Agent 如果收到 EOF，应重新连接本地端口。

## 7. BridgeSession 行为

### upstream

- `_connect_initial()`：首次连接并完成 PoW。
- `_pump_upstream()`：持续读取 upstream。
- upstream 断开：
  - 本地 Agent 会被关闭，使其看到 EOF；
  - 如果 `auto_reconnect=True`，后台 worker 重新连接并再次过 PoW；
  - 如果关闭自动重连，状态变为 `upstream_closed`，可手动 `reconnect`。

### 本地 listener

- 默认绑定 `127.0.0.1`，端口 0 自动选择。
- 同一时间只允许一个 Agent。
- Agent 断开后 upstream 不断。
- 没有 Agent 时收到的 upstream 数据会进入 bounded pending buffer，并在新
  Agent 连接时重放。

### time limit

- 默认 3600 秒。
- 由 `_timer_loop` 触发，到期后关闭 listener、Agent 和 upstream。
- `--no-timeout` 可关闭。

### logging

每个 run 记录：

- 完整 raw stream：`challenge_to_agent.bin`、`agent_to_challenge.bin`
- JSON 事件：`events.jsonl`
- 人类可读摘要：`transcript.log`

team key 不会写入任何日志。

---

## 8. Control 协议

control socket 是 Unix domain socket，JSON lines 请求/响应。

请求示例：

```json
{"cmd": "status"}
{"cmd": "events", "since": 0, "limit": 200}
{"cmd": "send", "data_b64": "...", "label": "human"}
{"cmd": "reconnect"}
{"cmd": "stop", "reason": "cli stop"}
```

响应示例：

```json
{"ok": true, "status": {...}}
{"ok": true, "events": [...]}
{"ok": true, "sent": 5}
```

权限为 `0600`，仅供本机同用户使用。

---

## 9. 安全要求

- `.env.local` / team key 文件必须 `0600`。
- 默认只监听 `127.0.0.1`。
- control socket `0600`。
- team key 只参与本地 HMAC；不发送、不记录、不写入 metadata。
- 人类 `send` 命令会写入真实 upstream，正式自主运行阶段应只给 Agent 使用本地
  端口，避免人工干预。

## 11. 已知限制 / TODO

1. 官方 ADK 和 solver 未发布，PoW 编码仍是猜测；拿到官方实现后需要校准。
2. 当前只支持 raw TCP + PoW；web / download 题应由 Agent 直接处理。
3. 每条会话仍只允许一个本地客户端；同题目的多个 worker 应使用不同会话的端口，见第 14 节。
4. 自动重连会创建新的 upstream 会话，题目内部状态可能丢失；Agent 应以
   `run.json` 中的 `state` / EOF 为信号判断是否重连。
5. 缺少 HTTP dashboard；目前人类检查通过 CLI + transcript 文件。
6. 未实现 platform API flag 提交；后续可接入 `CYPHER_PLATFORM_TOKEN`。
7. 未实现官方 Docker agent 运行时集成；目前假设 Agent 与 bridge 网络可达。
8. 多 challenge 并行运行时，`active.json` 只记录最新 run；其他 run 需要
   显式使用 `--challenge-id` / `--run-id` 或 `list` 查看。
   子会话创建不会修改 `active.json`。
9. `src` 布局已配置 setuptools，`uv sync` 会安装包；如果离线环境无法构建，
   需要保留已构建的 `.venv` 或改成 `PYTHONPATH=src` 方式。

## 13. Minimal Agent Unit（阶段 A）

### 目标

阶段 A 实现一个极简的 model-tool loop，作为后续长期自主 Agent 的基本工作单元。
设计上参考 DeepSeek Harness Minimal 的思想：

- 工具集非常小：`bash` + `str_replace_editor` + `report_flag`。
- 不自动注入大量上下文；challenge 描述作为任务内容提供。
- 模型主要靠 bash + 脚本探索和解题。
- 自动结束条件为 `max_seconds`、context window 触顶和 `report_flag`。
- 不做偏离检测、卡死检测、多任务检测。
- parent scheduler 暂缓；当前不引入 smolagents / Temporal / LangGraph。

### 模块

```text
src/incypher_agent/
├── __init__.py
├── __main__.py
├── cli.py          # run / doctor / smoke / show
├── config.py       # 读取 .env.local、解析 run.json、构造 AgentConfig
├── loop.py         # model-tool 主循环、时间/上下文预算
├── model.py        # OpenAI-compatible / DeepSeek 客户端
├── prompt.py       # 最小 system + 初始 user message
├── state.py        # state.json / events.jsonl / heartbeat / escalation / flag
└── tools.py        # bash / str_replace_editor / report_flag
```

### 模型配置

`.env.local` 需要：

```dotenv
DEEPSEEK_API_KEY=...
DEEPSEEK_BASE_URL=https://api.deepseek.com
```

API key 只从该 `.env.local` 读取，不再回退系统环境变量；缺失或格式非法时会报错退出。
模型名不再从 `.env.local` 读取，只通过 `--model` 或 `config.py` 中的默认值决定。

默认模型是 `deepseek-flash`，官方文档确认它支持 tool calls，OpenAI-compatible
base URL 为 `https://api.deepseek.com`。

真实模型连通性检查：

```bash
uv run python -m incypher_agent smoke
```

该命令会做一次真实的 chat completion 调用，不做伪装。

### 运行

先由 bridge 启动一个 run，然后：

```bash
uv run python -m incypher_agent run \
  --challenge-id overflow-ward \
  --run-id <run_id> \
  --max-seconds 3600 \
  --context-window-tokens 1000000 \
  --context-reserve-tokens 8000
```

Agent 启动时读取 `run.json` 中的：

- `agent_endpoint`
- `description_text`
- `challenge_md`
- `challenge_id` / `run_id`

### 循环行为

```text
while True:
    check max_seconds
    estimate next prompt tokens
    if estimated_prompt_tokens >= context_limit_tokens:
        stop with context_limit
    call model
    update usage baseline with prompt_tokens / completion_tokens
    if tool_calls:
        execute tools sequentially
        append tool results
        continue

    # 没有 tool call 不结束
    append a "continue working" nudge
```

其中：

```text
context_limit_tokens = context_window_tokens - context_reserve_tokens
```

只有以下情况退出：

- `report_flag`：成功，exit code 0。
- 超过 `max_seconds`：写 `agent/escalation.json`，exit code 10。
- 下一次输入估算达到 `context_limit_tokens`：写 `agent/escalation.json`，exit code 10。
- 模型调用连续失败：写 escalation，exit code 50。
- 用户 Ctrl-C：exit code 130。

### 状态文件

```text
.cypher_bridge/challenges/<challenge_id>/runs/<run_id>/agent/
├── state.json
├── events.jsonl
├── heartbeat
├── escalation.json
├── flag.json
├── agent.log
├── artifacts/
└── workspace/
```

`events.jsonl` 记录：

- model_request
- model_reply
- tool_call
- tool_result
- assistant_plain
- time_limit
- context_limit
- success

### 工具语义

- `bash`：在 workspace 内执行命令，有 timeout、输出截断、完整输出落 artifacts。
- `str_replace_editor`：view / create / str_replace / insert，路径限制在 workspace 内。
- `report_flag`：校验 flag pattern，写 `flag.json`，结束 run。

### 为什么测试里仍然有 scripted/fake model

需要区分两件事：

1. **真实模型验证**：用 `smoke` 和实际 `run` 完成，验证 DeepSeek API、
   tool calling、prompt、真实解题效果。
2. **确定性回归测试**：用 scripted model 注入固定的 tool call 序列，验证
   loop / tool / state / hard limit 不依赖网络和模型随机性。

scripted model 不是用来替代真实模型，而是像单元测试中的 fake HTTP server
一样，让 CI 可以在没有 API key、没有网络、没有费用的情况下验证 harness 契约。
真实模型是否好用，仍然必须通过 live run 验证。

### 后续阶段

- 阶段 B：上下文压缩、checkpoint、restart、长时间运行验证。
- 阶段 C：真实 bridge + 真实 challenge 的 live 测试。
- 阶段 D：讨论 parent scheduler。
- 阶段 E：scheduler 可以先做简单进程 supervisor + SQLite；Temporal 只在确实
  需要工作流 durability 时再考虑。

### 明确不做

- 不复用 sibling 项目的 smolagents / Temporal / broker 实现。
- 不自动注入大型 AGENTS.md / skill catalog。
- 不在阶段 A 做语义偏离检测。
- 不在阶段 A 引入多 agent 并行。

## 14. Bridge 多会话（不包含 Agent / 调度器）

### 模型与接口

`serve` 默认最多管理 4 条活跃会话（包括主 run），最多同时执行 1 次 upstream
建连 / PoW 握手。通过 `--max-sessions` 和 `--max-handshakes` 调整；重连也使用
同一握手额度。额度仅覆盖一个管理进程，不是跨进程的全局限额。

```bash
uv run python -m incypher_bridge serve \
  --target 47.236.162.54:30151 --challenge-id example --run-id primary \
  --max-sessions 4 --max-handshakes 1

uv run python -m incypher_bridge session-create \
  --challenge-id example --run-id primary --new-run-id worker-a
uv run python -m incypher_bridge session-create \
  --challenge-id example --run-id primary --new-run-id worker-b
uv run python -m incypher_bridge sessions --challenge-id example --run-id primary

uv run python -m incypher_bridge status --challenge-id example --run-id worker-a --json
uv run python -m incypher_bridge reconnect --challenge-id example --run-id worker-a
uv run python -m incypher_bridge stop --challenge-id example --run-id worker-a
```

`session-create` 和 `sessions` 输出 JSON。创建是异步的；调用方应轮询直到目标
会话 `state == "ready"` 且 `agent_endpoint` 非空，然后让模拟客户端或 worker
连接该会话的端口。握手失败时会话进入 `stopped`，通过 `last_error` 查看原因。

主 run control socket 新增：

```json
{"cmd": "session-create", "run_id": "worker-a"}
{"cmd": "sessions"}
```

创建响应包含 `ok`、`created` 和 `status`。同一个管理器内重复提交相同 run id
返回原会话，不重复建连或追加初始化日志；已经停止的 id 也不会隐式重新创建。
新的尝试需要新的 id。已有目录但不属于当前管理器的 id 会被拒绝，防止覆盖日志。
`serve` 同样拒绝复用已有 run 目录；省略 `--run-id` 会自动生成新的 id。
`sessions` 返回所有已创建会话（包括停止的记录）及额度；停止的会话不占活跃额度。

子会话使用已有目录布局 `challenges/<challenge_id>/runs/<child_run_id>/`，
`run.json` 增加 `parent_run_id`。每条会话保留自己的 control socket，因此
`status` / `observe` / `send` / `reconnect` / `stop` 继续用原有 run selector。
主 run 的 `status` 和日志仅代表主连接；总览使用 `sessions`。

### 生命周期和边界

- 客户端断开后，该会话 upstream 保留，重接原端口可以继续原会话并接收缓存。
- 同一会话的第二个客户端仍收到 busy；并发依靠不同会话实现。
- 自动或手动重建 upstream 时关闭旧客户端、清空旧连接缓存，并递增
  `upstream_generation`。其他会话不受影响。
- 停止子 run 只关闭该子会话；停止主 run 或主 run 到期会关闭全部子会话。
  因此 `stop --run-id primary` 表示结束整个 bridge 管理进程。
- 等待握手额度可以取消，PoW 求解定期检查取消信号；停止时会关闭已建立的握手
  socket。尚在执行的操作系统 DNS / TCP connect 仍可能等待其底层超时，返回后
  不会被采纳为活跃 upstream。
- 连接之间不共享协议字节，但可能访问相同的远端容器、文件系统或数据库。
  bridge 不保证远端题目状态隔离。
- 尚未实现会话自动回收策略；不用的子会话应显式 stop，或随主 run 到期关闭。

### 无真实 Agent 的验证

```bash
uv run python -m unittest tests.test_bridge tests.test_bridge_sessions tests.test_pow -v
```

使用本地 mock PoW gate 和普通 socket，验证并发字节及日志隔离、busy、重复创建、
额度限制、断开重接、手动及自动重连、握手失败和创建期间关闭。

可选的真实接口连接探测（不会由 unittest 自动运行）：

```bash
uv run python -m tests.bridge_connection_probe \
  --host 47.236.162.54 --port 30151 --sessions 3
```

此脚本读取本地私密 team key，建立独立 PoW 会话并让普通 TCP 客户端同时附着，
验证不同 nonce 和存活状态。只发送 PoW 答案，不发送题目命令、不调用模型或真实
Agent；测试结束关闭所有会话并清理临时日志。接口地址仅用于手动测试，不作为默认目标。
